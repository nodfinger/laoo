# LAOO UX/UI Standard

## การจัดระดับตำแหน่งสำหรับการอนุมัติ

- บริษัทกำหนดวิธีเริ่มต้นได้ที่กำหนดค่าระบบ ส่วนการอนุมัติข้อมูลและเอกสาร: จัดตามชื่อ จัดตามรหัสย่อ หรือจัดตามลำดับของข้อมูลระดับตำแหน่งงาน
- รูปแบบอนุมัติชนิดตามระดับตำแหน่งขึ้นไปเลือกวิธีได้แยกแต่ละรูปแบบ โดยเริ่มต้นจากค่าบริษัทเมื่อยังไม่ได้บันทึกวิธีเฉพาะ
- เรียงจากน้อยไปมากและถือว่ารายการที่เรียงหลังเป็นระดับสูงกว่า; ต้องไม่ส่งอนุมัติเมื่อข้อมูลที่ใช้เรียงว่างหรือซ้ำจนระบุลำดับไม่ได้

## การอนุมัติข้อมูลและเอกสารตามตำแหน่งงาน

- หากบริษัทเปิดใช้ระบบการอนุมัติข้อมูล-เอกสาร Backend ต้องตรวจการตั้งค่าการอนุมัติของเมนูหรือประเภทข้อมูลและรูปแบบอนุมัติที่กำหนดไว้ก่อนดำเนินการ โดยไม่สมมติว่ารายการได้รับอนุมัติแล้วหากไม่พบการตั้งค่า
- ตัวเลือกหน่วยงาน **เจาะจงตำแหน่งงานนี้เท่านั้น** ส่งอนุมัติไปยังตำแหน่งงานที่เลือกโดยตรง
- ตัวเลือก **แผนกเดียวกัน** ส่งไปยังตำแหน่งงานที่เลือกซึ่งอยู่แผนกเดียวกับผู้บันทึก เช่น ผู้บันทึกอยู่แผนกบัญชี ส่งไปขออนุมัติที่หัวหน้าแผนกบัญชี
- ตัวเลือก **ฝ่ายเดียวกัน** ส่งไปยังตำแหน่งงานที่เลือกซึ่งอยู่ฝ่ายเดียวกับผู้บันทึก เช่น ผู้บันทึกอยู่แผนกบัญชี ส่งไปขออนุมัติที่ผู้จัดการฝ่ายบัญชี
- แสดงคำอธิบายตามตัวเลือกในหน้ากำหนดรูปแบบ และตรวจบริษัท สิทธิ์ และหน่วยงานของผู้บันทึกก่อนส่งอนุมัติทุกครั้ง
- ให้ตรวจพนักงานที่ผูกกับผู้ Login ในบริษัทปัจจุบันก่อน: หากเมนูนั้นกำหนดลำดับเฉพาะบุคคลให้ใช้ลำดับนั้นแทนรูปแบบปกติ หากไม่มีการกำหนดเฉพาะบุคคลให้ใช้รูปแบบอนุมัติปกติของเมนู โดยตรวจสิทธิ์และบริษัทของพนักงานและผู้อนุมัติทุกครั้ง; หากพบการตั้งค่าเฉพาะบุคคลแต่ข้อมูลไม่ครบหรือใช้ไม่ได้ ห้ามข้ามไปใช้รูปแบบปกติโดยเงียบ

## การแสดงชื่อพนักงาน

- หน้าจอที่แสดงชื่อพนักงานต้องใช้รูปแบบชื่อที่บริษัทกำหนดจากค่ากลาง: ชื่อจริง, ชื่อเล่น หรือชื่อจริงและชื่อเล่น โดยคงข้อมูลชื่อจริงและชื่อเล่นแยกกัน ไม่เปลี่ยนข้อมูลต้นฉบับหรือรหัสอ้างอิง
- หากชื่อเล่นว่าง ให้แสดงชื่อจริงแทน และหากชื่อจริงว่างให้แสดงชื่อเล่นแทน หากไม่พบทั้งสองให้แสดงเครื่องหมาย `-`; ข้อมูลที่เป็นชื่อบุคคลประเภทอื่นหรือชื่อที่เก็บเป็น snapshot ต้องรักษาความหมายเดิมและไม่อนุมานว่าเป็นพนักงาน
- การเปลี่ยนรูปแบบเป็นการแสดงผลเท่านั้น ไม่เปลี่ยนสิทธิ์ ขอบเขตข้อมูล หรือข้อมูลประวัติ และต้องใช้ค่าของบริษัทผู้ใช้งานปัจจุบัน

ไฟล์นี้เป็นมาตรฐาน UX/UI กลางของ Project `laoo` และเป็นจุดเริ่มต้นก่อนอ่านมาตรฐานเฉพาะประเภทหน้าจอ

## Required Reading by Screen Type

- หน้า List หรือ Card: อ่าน `LIST_CARD_UI_STANDARD.md` และ `PAGINATION_UI_STANDARD.md`
- หน้าจอ CRUD ที่ต้องการเทียบต้นแบบ: อ่าน `MASTER_DATA_CRUD_UI_STANDARD.md` เพิ่มเติม โดยใช้หน้า `05002 รหัสพื้นฐาน` เป็น Visual Reference
- หน้า Action (Add/Edit/View): อ่าน `ACTION_UI_STANDARD.md`; สำหรับ `ScreenType = 1` (CRUD) ต้องใช้ Action Style ตามเอกสารนี้เสมอ ทั้งพื้นผิวสีขาว มุมกรอบและปุ่ม `4px`, Caption สีดำ, Icon ตาม User Style และ TextBox/ComboBox มีกรอบมุมโค้ง `4px`
- Popup, Dialog, Alert และ Confirm: อ่าน `POPUP_UI_STANDARD.md`
- งานที่เกี่ยวกับข้อความหรือขนาดตัวอักษร: อ่าน `TYPOGRAPHY_STANDARD.md`
- ถ้างานครอบคลุมหลายประเภท ต้องอ่านทุกไฟล์ที่เกี่ยวข้องก่อนแก้ไข

## Common Design Tokens

- พื้นหลังทุกหน้าจอใช้ `LaooColors.background` (`#F8F9FB`)
- สีหลักและสีสถานะใช้งานอ่านจาก `workspaceThemeController.value.primary` หรือ `WorkspaceThemePreset.primary` ของ User ที่ Login
- Card ใช้พื้นสีขาว ไม่มีเส้นกรอบสี และมุมโค้ง `LaooRadius.xs` (`4px`)
- Margin รอบ Content ทั่วไปใช้ `LaooLayout.cardMargin` (`10px`); หน้า List ใช้ `24px` ตาม `LIST_CARD_UI_STANDARD.md`
- Padding ภายใน Card ใช้ `LaooLayout.cardPadding` (`10px`)
- ระยะทั่วไประหว่าง Card/Section ใช้ `LaooLayout.cardSpacing` (`10px`); หน้า List ใช้ระยะระหว่าง Section และ Card รายการ `8px` ตาม `LIST_CARD_UI_STANDARD.md`
- เส้นคั่นทั่วไปใช้ `LaooColors.border` สีเทาอ่อนและบาง; เส้นคั่นใน Table/List ใช้ Semantic Border Color ตาม User Style และความหนาตาม `LIST_CARD_UI_STANDARD.md`
- TextBox และ ComboBox ทุกหน้าจอ โดยเฉพาะภายใน Popup ต้องเป็นกรอบรอบช่องแบบ `OutlineInputBorder` เส้นสีเทาจางจาก Neutral/Border Token กลาง และมุมโค้ง `LaooRadius.xs` (`4px`) เสมอ ห้ามใช้เฉพาะเส้นใต้ ห้ามไม่มีกรอบ และห้ามใช้สี Primary เป็นกรอบในสถานะปกติ
- สีที่สื่อการโต้ตอบหรือเอกลักษณ์ของผู้ใช้ เช่น Focus Border, Floating Label เมื่อช่องมีข้อมูลหรือ Focus, Cursor, Selected Item, Icon และปุ่ม Action ต้องอ่านจาก `workspaceThemeController.value`/User Profile Theme ผ่าน Semantic Token กลาง ห้าม hardcode สีรายหน้าจอ; สีข้อความข้อมูลใช้ Semantic Text Color ของ Theme
- สีพื้นขาว สีเทากลาง และสีสถานะ Error/Delete/Warning เป็น Semantic Color ตามมาตรฐาน ไม่ถูกแทนด้วยสี Primary ของ User; สถานะ Disabled ต้องใช้ Disabled/Neutral Token และยังคงกรอบเทาจางกับมุม `4px`
- Caption หลักของหน้า `List`, `Card`, `Action` และ `Popup/Dialog` ทุกประเภทใช้ `fontSize: 18`, `fontWeight: FontWeight.w700` และ `LaooColors.pageCaption` ซึ่งต้องเป็นสีดำ ส่วน Icon ใช้สีหลักของ User Style; Popup ยืนยันลบใช้ Icon สี Error/Delete และ Caption สีดำ
- ห้ามใช้ `Colors.green`, `Colors.blue` หรือสีหลักแบบ hardcode; สีแดงใช้ได้เฉพาะ Error, Delete, Offline หรือสถานะไม่ใช้งานตามข้อกำหนด
- เมื่อ User เปลี่ยน Style สีทุกส่วนที่อิง User Styleต้องเปลี่ยนทันทีและต้องไม่กระทบ User คนอื่น

## Common Behavior

- วันที่ที่แสดงแก่ผู้ใช้ทุกหน้าจอ ทั้ง List/Card, Action, Popup, รายละเอียด และการแจ้งเตือน ต้องแสดงวันเดือนปีเป็น `dd/MM/yyyy` โดยมีเลขวันและเดือนสองหลักเสมอ หากต้องแสดงเวลาด้วยให้ตามหลังวันที่โดยคง `dd/MM/yyyy` เป็นส่วนวันที่; วันที่ไม่มีค่าให้แสดงสถานะว่างที่เหมาะสม ห้ามแสดง ISO หรือ Timestamp ดิบแก่ผู้ใช้ ใช้ `CompanyDateFormatter` และรูปแบบปีของบริษัทตามข้อกำหนดเดิม ส่วนค่าที่ส่งหรือเก็บใน API/Database ยังคงเป็นรูปแบบข้อมูลเดิม
- ช่องค้นหาหรือ ComboBox ที่เลือกข้อมูลจาก Popup และอนุญาตให้ไม่มีค่า ต้องมีปุ่มล้างค่าในช่องเมื่อมีรายการที่เลือก กดแล้วคืนเป็นค่าว่างโดยไม่เปลี่ยนข้อมูลอื่น และยังให้ Validation บังคับช่องที่จำเป็นทำงานตามเดิม; ไม่แสดงปุ่มล้างสำหรับช่องที่ห้ามเป็นค่าว่างหรือผู้ใช้ไม่มีสิทธิ์แก้ไข
- Shared Workspace Header ต้องใช้พื้นที่แนวตั้งอย่างประหยัด: Desktop สูง `52px` และ Mobile สูง `56px`
- Desktop ต้องวางปุ่มหน้าแรก เมนูลัด และเมนูผู้ใช้ในแถวเดียวกัน; แสดงเมนูลัดโดยตรงได้สูงสุด `5` รายการตามพื้นที่ และรวมรายการที่เกินไว้ใน Popup `เพิ่มเติม`
- Mobile แสดงเมนูลัดทั้งหมดผ่าน Popup รูปดาว และใช้ User Menu แบบ Compact; คำอธิบายสิทธิ์/ประเภทผู้ใช้แสดงภายใน User Menu ไม่วางเป็นบรรทัดที่สองบน Header
- คำสั่งออกจากระบบอยู่ภายใน User Menu เพียงตำแหน่งเดียว ห้ามวางปุ่มซ้ำบน Workspace Header
- Caption และชื่อเมนูต้องอ่านจาก Navigation API/`TDADMainMenu.MenuName` ผ่าน Resolver กลาง ห้าม hardcode แยกจาก Sidebar
- ทุกหน้าจอที่ผูก MenuCode ต้องมีปุ่ม Icon ดาวอยู่ถัดจาก Caption เพื่อเพิ่ม/นำออกจากเมนูลัดของผู้ Login และสถานะต้องเชื่อมกับเมนูลัดส่วนกลางทันที
- ดาวโปร่งคือยังไม่เป็นเมนูลัด ดาวทึบคือเป็นเมนูลัด; กดเพื่อสลับสถานะและบันทึกเฉพาะ User ที่ Login เมื่อสำเร็จให้อัปเดตดาวและแถบเมนูลัดทันที หากบันทึกไม่สำเร็จให้คงสถานะเดิมและแจ้งข้อผิดพลาด
- มุมมอง Card ของหน้ารายการใช้หน้ากลุ่มสิทธิ์ `10003` เป็น Visual Reference ตามรายละเอียดใน `LIST_CARD_UI_STANDARD.md` โดยใช้สีจาก User Style และแสดง Action ตาม Permission
- ทุกหน้าจอต้องเต็ม Content Area ภายใน Shared Workspace และไม่สร้าง Shell ซ้อน
- เมื่อ Content Area แคบกว่า `900px` ต้องใช้ Responsive Layout ที่ไม่เกิด Overflow
- Action ทุกชนิดต้องตรวจทั้ง `ScreenType` และ Permission ของ User; Backend ต้องตรวจซ้ำ
- ผู้ใช้ที่มีสิทธิ์แสดงหน้าจอหลักต้องอ่านข้อมูลประกอบที่จำเป็นต่อหน้าจอนั้นได้อย่างน้อยแบบอ่านอย่างเดียว แม้ไม่มีสิทธิ์เข้าหน้าจัดการข้อมูลประกอบ เช่น รหัสพื้นฐาน โดย Backend ต้องตรวจสิทธิ์หน้าจอหลัก แพ็กเกจและขอบเขตเจ้าของข้อมูลทุกครั้ง และจำกัดเฉพาะข้อมูลที่หน้าจอนั้นจำเป็นต้องใช้
- สิทธิ์อ่านข้อมูลประกอบไม่ถือเป็นสิทธิ์เข้าหน้าจัดการข้อมูลหลักทั้งหมด และไม่ให้สิทธิ์เพิ่ม แก้ไข หรือลบโดยอัตโนมัติ; แต่ละหน้าต้องกำหนดรายการข้อมูลประกอบที่อนุญาตอย่างชัดเจนและตรวจสิทธิ์ดำเนินการแยกตามปกติ
- Error ทุกหน้าจอต้องแสดงข้อความหลักพร้อม `รายละเอียดเพิ่มเติม` ที่บอกสาเหตุหรือสิ่งที่ผู้ใช้ควรทำต่อ ตาม `POPUP_UI_STANDARD.md`; ห้ามแสดงข้อความ API แบบกว้างเพียงบรรทัดเดียว
- แก้ UX/UI โดยไม่เปลี่ยน API, SQL, Repository หรือ Business Logic เว้นแต่คำสั่งระบุชัดเจน
- หลังแก้ต้องตรวจ Responsive, Overflow, `dart format` และ `dart analyze` พร้อมสรุปไฟล์ที่แก้
